# README: Архитектура системы для пекарни (v0.1)

## 1. Общее описание

Система автоматизирует работу пекарни с собственной производственной. На текущем этапе охватывает **меню, стоп-листы и заказы**. Учёт остатков, касса и полноценная производственная ERP — вне скоупа.

Ключевой принцип: **Frontpad остаётся системой для кассовых операций и заказов, но не является единственным источником истины.** Новые интерфейсы для персонала строятся как самостоятельный слой, интегрированный с Frontpad через хуки.

## 2. Компоненты системы

### 2.1. Client Service (Client WS)

Отвечает за публичный сайт и админку сайта.

**Возможности:**

- Отдаёт актуальное меню (позиции, описания, изображения, цены).
- Админка: создание и редактирование меню, управление изображениями и описаниями.
- Управление стоп-листами (администратор — полный доступ; оператор — только добавление/снятие стопов).
- Все изменения сохраняются в БД через Core Service.

### 2.2. Staff Service (Staff WS)

Единая точка входа для интерфейсов персонала: оператор (OPER), повар (COOK), доставщик (DEV).

**Роли и права:**

- **OPER (оператор):** видит новые заказы, может редактировать заказ (CRUD), назначает доступного курьера. Может ставить и снимать стоп-листы.
- **COOK (повар):** только чтение. Видит заказ на табло без лишних данных (только состав заказа для приготовления).
- **DEV (доставщик):** видит только заказы, назначенные ему оператором. Может менять статус заказа (`в пути`, `доставлен`, `задерживаюсь`).

**Механизм оповещения:** WebSocket. При переподключении клиент запрашивает актуальный снимок состояния (snapshot), затем подписывается на новые события (delta).

**Разделение каналов:** отдельные комнаты/топики для `oper`, `cook`, `dev:{courier_id}`.

### 2.3. Core Service (Core Serv)

Центральный сервис бизнес-логики и единственная точка работы с БД.

**Ответственность:**

- Валидация бизнес-правил (например, проверка прав на снятие стоп-листа, проверка принадлежности заказа курьеру).
- Управление транзакциями.
- Преобразование «сырых» данных из хуков в доменные модели.
- Публикация доменных событий для Staff WS (через outbox-таблицу).

**Важно:** Core Service не является простой CRUD-обёрткой. Если в будущем он начнёт разрастаться, из него будут выделены отдельные модули (MenuService, OrderService), но единая точка входа сохранится.

### 2.4. Хуки (Hooks)

Точки входа внешних событий. **Не содержат бизнес-логики** и не являются синхронным мостом в Core Service.

**Общий паттерн работы хука:**

1. Принять запрос.
2. Проверить подпись/источник и идемпотентность.
3. Записать «сырое» событие в таблицу `inbox`.
4. Немедленно вернуть `200 OK` отправителю.

**Обработка события** происходит асинхронно в Core Service (воркер читает `inbox`).

#### 2.4.1. Frontpad Hook

- Принимает события о новых заказах из Frontpad.
- Идемпотентность: проверка по `order_id` + тип события.
- Запись в `inbox_orders`.
- Немедленный ответ `200 OK`.

#### 2.4.2. Ucassa Hook

- Принимает уведомления об оплате от ЮKassa.
- **Безопасность:**
  - Проверка подписи (MD5 или PKCS#7 — по согласованию с ЮKassa).
  - Проверка IP-адреса отправителя (список IP запрашивается у менеджера ЮKassa).
  - Идемпотентность по `invoiceId`.
- Запись в `inbox_payments`.
- Немедленный ответ `200 OK`.
- **Важно:** сумма и назначение платежа формируются на сервере, не доверяем данным из браузера.

### 2.5. База данных (DB)

Единая БД системы.

**Основные сущности:**

- Позиции меню, описания, изображения.
- Стоп-листы.
- Заказы и их статусы.
- Курьеры (с `courier_id` для проверки прав).
- `inbox_orders`, `inbox_payments` — для приёма событий из хуков.
- `outbox_events` — для асинхронной публикации доменных событий.

## 3. Потоки данных

### 3.1. Создание заказа (Frontpad → Кухня/Оператор)

1. Оператор оформляет заказ в Frontpad.
2. Frontpad отправляет событие на **Frontpad Hook**.
3. Хук проверяет идемпотентность, пишет в `inbox_orders`, отвечает `200 OK`.
4. **Core Service** (воркер) читает `inbox_orders`, создаёт заказ в БД, пишет событие `OrderCreated` в `outbox_events`.
5. Core Service рассылает событие в **Staff Service**.
6. Staff Service уведомляет клиентов через WebSocket:
   - `oper` — полный заказ.
   - `cook` — только состав для приготовления.

### 3.2. Назначение курьера (Оператор → Доставщик)

1. Оператор в Staff WS назначает курьера на заказ.
2. Запрос идёт в Core Service, который проверяет права и обновляет заказ в БД.
3. Core Service публикует событие `CourierAssigned` в `outbox_events`.
4. Staff Service уведомляет конкретного курьера (комната `dev:{courier_id}`).

### 3.3. Оплата (ЮKassa → Система)

1. Клиент на сайте инициирует оплату через модуль ЮKassa (данные передаются на сервер для формирования суммы).
2. ЮKassa отправляет уведомление на **Ucassa Hook**.
3. Хук проверяет подпись, IP, идемпотентность; пишет в `inbox_payments`; отвечает `200 OK`.
4. **Core Service** (воркер) читает `inbox_payments`, обновляет статус оплаты заказа, публикует событие `PaymentConfirmed` в `outbox_events`.
5. Staff Service уведомляет оператора и курьера.

## 4. Принятые архитектурные решения

| Решение                                               | Обоснование                                                                                                                                                       |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Роутер убран**                                      | Зоны ответственности разделены на уровне сервисов; дополнительный слой маршрутизации создаёт лишнюю точку отказа и задержку.                                      |
| **Хуки не являются синхронным мостом в Core Service** | Платёжные системы ждут быстрый ответ; синхронная цепочка создаёт задержку и хрупкость. Паттерн: принять → сохранить в `inbox` → ответить → обработать асинхронно. |
| **Брокер сообщений не вводится на текущем этапе**     | Масштаб не требует внешнего брокера. Outbox-таблица в БД решает задачу надёжной публикации событий. При росте — переход на Redis Pub/Sub или RabbitMQ.            |
| **Core Service — не просто CRUD-обёртка**             | Отвечает за бизнес-правила, транзакции, преобразование данных из хуков.                                                                                           |
| **WebSocket с комнатами по ролям**                    | Снижает нагрузку и упрощает безопасность: курьер не получает события о чужих заказах.                                                                             |
| **Snapshot + delta при переподключении**              | WebSocket не гарантирует доставку; клиент при переподключении запрашивает актуальное состояние.                                                                   |
| **Идемпотентность хуков**                             | Защита от повторных уведомлений (ЮKassa, Frontpad).                                                                                                               |
| **Проверка прав на уровне Core Service**              | Не доверяем фильтрации на фронтенде; курьер может менять статус только своих заказов.                                                                             |
| **request_id сквозь все сервисы**                     | Упрощает отладку распределённой системы.                                                                                                                          |

## 5. Что вне скоупа на текущем этапе

- Учёт остатков сырья и готовой продукции.
- Полноценная касса.
- Производственное планирование (замесы, партии, расстойка).
- Аналитика и отчётность.
- Внешний брокер сообщений.

## 6. Направления для будущего развития

- Выделение отдельных модулей из Core Service при росте бизнес-логики.
- Введение Redis Pub/Sub или RabbitMQ при масштабировании Staff Service на несколько инстансов.
- Расширение производственного контура (рецептуры, технологические карты, партии).
- Мониторинг и алертинг на основе `request_id`.
